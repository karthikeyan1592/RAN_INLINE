# Architecture Evaluation: Open, Vendor-Portable GPU L1 Acceleration for O-RAN ("Open Inline")

## TL;DR
- **The frozen doc's lookaside-first + "Track-2" deferral of GPU-initiated networking is the correct call today.** A genuinely open, vendor-portable, zero-copy + GPU-initiated *inline* L1 is NOT achievable in mainline Linux in 2026: true zero-copy NIC→GPU DMA works robustly only on mlx5 (NVIDIA/Mellanox) NICs even when the GPU is AMD/Intel, and open "GPU-initiated" networking (UCCL-EP, NCCL-GIN Proxy) is a CPU-proxy emulation, not device-initiated doorbell ringing — and none of it is validated for eCPRI's 500 µs deadlines.
- **The GPU BBDev PMD first deliverable is feasible and genuinely novel** (no GPU BBDev PMD exists — all in-tree drivers are FPGA/ASIC), but effort is moderate-to-high, and there are two hidden landmines: DPDK's `gpudev` library is CUDA-only and unhelpful for a portable OpenCL PMD, and **HARQ soft-buffer combining** (ACC100 keeps HARQ on-card) is the single biggest correctness/latency risk on a lookaside GPU.
- **Several §8 claims are shaky and two should be unfrozen.** The CXL Type-3 "system-ram NUMA shared between CPU and GPU" story is the weakest link — the anchor CCCL numbers are real but were measured with CUDA `cudaHostRegister`+`cudaMemcpyAsync` on a discrete H100, a path with **no proven OpenCL/AMD equivalent** — and IISc HACC has **no CXL hardware at all**; the SYCL/OpenCL choice also carries a real dmabuf-interop blocker on the exact hardware (AMD MI210) available at IISc.

## Key Findings

**1. Zero-copy NIC→GPU is real but NIC-locked, not vendor-portable.** The `ibv_reg_dmabuf_mr()` verb (rdma-core) is the open, standard mechanism. dmabuf export from GPU VRAM works on AMD ROCm (`hsa_amd_portable_export_dmabuf`) and NVIDIA (`cuMemGetHandleForAddressRange`). But the *importer* side — the NIC driver — is the bottleneck: robust dmabuf peer-memory import is mature only on **mlx5 (NVIDIA/Mellanox ConnectX)**. Intel `irdma` (E810) gained dmabuf-pinned-MR support only via a follow-on patch (Zhu Yanjun) that used a habanalabs exporter and historically leaned on ODP-capable NICs. So the "open datapath" ironically still depends on buying NVIDIA/Mellanox NICs — a fact the doc should state explicitly.

**2. Open GPU-initiated networking = CPU-proxy emulation, not true device-initiated.** UCCL-EP (arXiv:2512.19849, OSDI'26, Apache-2.0, github.com/uccl-project/uccl) and NCCL-GIN's "Proxy" backend (arXiv:2511.15076) both explicitly *replace* GPU-initiated RDMA with a GPU→CPU lock-free command channel; the CPU issues the verbs. True device-initiated doorbell ringing (NVIDIA IBGDA / DOCA GPUNetIO / GDAKI) remains NVIDIA-ConnectX-locked and has **no AMD equivalent** — AMD has no GPUNetIO. This vindicates the doc's Track-2 deferral. Crucially, all this work targets **AI collectives (large messages)**, not eCPRI (tiny packets, hard 500 µs deadlines); there is no open project doing GPU-driven eCPRI/U-plane.

**3. The GPU BBDev PMD is novel and the AAL seam is the right offload point.** Confirmed: every in-tree DPDK BBDev PMD is FPGA/ASIC (Intel ACC100/ACC200 "Mount Bryce", FPGA 5GNR "Vista/Arrow Creek", AccelerComm/AMD-Xilinx T2). No GPU BBDev PMD exists. OAI's `nrLDPC_coding` plugin interface (shlib `_t2`) is the real, working AAL seam, and O-RAN WG6 explicitly names DPDK BBDev as the FEC AAL realization. This is a clean, defensible novelty claim.

**4. The anchor numbers check out but carry a hidden portability caveat.** "Six Times to Spare" (arXiv:2602.04652) is real and correctly characterized, but its GPU is *integrated* (Blackwell GB10 on DGX Spark) and it runs high-level Sionna/TensorFlow, so its slot envelope is an optimistic reference for a discrete-GPU lookaside design. The CCCL paper (arXiv:2602.22457) confirms ~20 GB/s and 658 ns for GPU↔CXL — but on a discrete NVIDIA H100 via `cudaHostRegister`+`cudaMemcpyAsync` streaming DMA, with **no demonstrated OpenCL/AMD equivalent** of that pin-and-DMA path.

## Details

### RESEARCH QUESTION 1 — Is a better (zero-copy + GPU-initiated inline) open architecture achievable today?

**Verdict: No — not with open/vendor-portable standards on non-NVIDIA hardware. The frozen lookaside-first + Track-2 split is correct.**

- **DMA-BUF P2P into non-NVIDIA GPU VRAM.** The kernel plumbing has been upstream since Linux 5.12 (Jianxin Xiong's series added `ib_umem_dmabuf_get` and the mlx5 importer). AMD's export side works: ROCm exposes `hsa_amd_portable_export_dmabuf`, and the current amdgpu path reports `DMAbuf Support: YES` in `rocminfo`. The requirements are **large-BAR** (all VRAM exposed via PCI BARs), IOMMU in passthrough, and same PCIe root complex/switch — per AMD's ROCmRDMA/ROCnRDMA (PeerDirect) documentation. The catch is the NIC importer: production dmabuf-MR import is mature on **mlx5 only**. Intel `irdma` (E810) dmabuf-pinned-MR is a later, narrower patch; Broadcom `bnxt_re` and others were touched by the original series but are less proven. **Conclusion: "zero-copy, vendor-portable NIC→GPU in mainline today" is false on the NIC axis.** It is genuinely zero-copy (NIC DMAs into VRAM, no bounce buffer) *only* on the mlx5 + AMD/Intel-GPU combination — not vendor-neutral on the NIC dimension. The doc's DMA-BUF+RoCE ingress decision is sound but should acknowledge the mlx5 dependency.

- **GPU-initiated networking, open options.** UCCL (arXiv:2504.17307) and UCCL-EP (arXiv:2512.19849, OSDI'26) are the leading open, vendor-agnostic efforts, and AMD's Primus/TheRock adopt them. But their explicit architecture is a **GPU→CPU-proxy** split: "instead of having GPUs post RDMA operations directly to the NIC (as in NVIDIA's IBGDA model), each GPU forwards lightweight control commands … to the CPU," which then issues GPUDirect RDMA via libibverbs. NCCL-GIN (arXiv:2511.15076) has a dual backend: GDAKI (DOCA GPUNetIO, NVIDIA-only) and a Proxy backend (CPU-mediated, "arbitrary RDMA-capable NICs"). So: **a GPU on AMD/Intel cannot ring NIC doorbells / post WQEs from device code via any open API today.** ROC_SHMEM/rocSHMEM and Intel SHMEM exist for PGAS, but device-initiated transport still bottoms out on NVSHMEM-IBGDA-style hardware coupling that AMD lacks. eCPRI-fronthaul feasibility is essentially unexplored — all cited work targets large-message AI collectives, where µs-scale CPU-proxy latency is tolerable; for U-plane with 500 µs slot budgets and tiny packets, the CPU-proxy round trip is a real risk and there is no published open result.

- **SYCL/OpenCL interop with these datapaths (a real, under-appreciated blocker).** The open path exists on paper: OpenCL `cl_khr_external_memory` with `CL_EXTERNAL_MEMORY_HANDLE_OPAQUE_FD_KHR`, and ARM's older `cl_arm_import_memory` with `CL_IMPORT_TYPE_DMA_BUF_ARM`. But `cl_khr_external_memory` support is uneven across AMD/Intel/NVIDIA OpenCL runtimes, and importing a *dmabuf* specifically (vs. an opaque fd from another CL context) is not uniformly implemented. SYCL adds another layer: AdaptiveCpp/DPC++ external-memory import is nascent. **This interop story is a hidden blocker for the frozen SYCL/OpenCL choice** and should be prototyped before freeze: the full "NIC dmabuf → GPU kernel reads it" chain must be validated end-to-end on the target runtime, not assumed.

- **Inline vs lookaside in BBDev/AAL.** BBDev is **inherently lookaside**: `rte_bbdev_op_ldpc_dec` takes an input mbuf (LLR virtual circular buffer) and produces a hard-output mbuf; the op is enqueued/dequeued — a classic accelerator-offload model (DecodeX, arXiv:2511.02952, confirms ACC100 and OAI's CUDA LDPC decoder both follow the lookaside model). O-RAN WG6 AAL does define look-aside, inline, and hybrid modes (per CLOUD-REF v02.00), but the *FEC/BBDev* realization is lookaside. **True inline L1 (Aerial ARC/cuPHY) means the entire high-PHY — FFT, channel estimation, equalization, demap, LDPC — is GPU-resident with fronthaul eCPRI DMA'd straight into GPU memory, no per-CB host round trip** (NVIDIA: "the entire L1 processing pipeline and corresponding data are contained within the GPU kernels and DRAM on the same converged card"). No open project does inline GPU L1; OAI+Aerial uses proprietary cuPHY via a FAPI split. So the doc's lookaside-first choice is the only open option that exists; inline is a multi-year systems effort, correctly deferred.

- **Alternative architectures.** (a) *Full-PHY-on-GPU with CPU-driven DPDK ingress + persistent GPU kernels polling pinned host memory* — the l2fwd-nv pattern; the realistic "poor man's inline," but a systems paper, and it needs the persistent-kernel + doorbell story AMD OpenCL doesn't cleanly support. (b) *P4/SmartNIC fronthaul termination feeding GPU* — viable but adds a SmartNIC dependency and is orthogonal to the FEC novelty. (c) *AMD's answer to Aerial* — there is none; AMD's RAN play is the Xilinx T1/T2 lookaside FPGA cards (AccelerComm BBDEV/DPDK L1 offload on Zynq UltraScale+ RFSoC) and Alveo, not a GPU inline stack. (d) *CXL.cache / CXL 3.x back-invalidation for coherent NIC/GPU sharing* — no shipping hardware pairs a coherent CXL.cache device with a discrete GPU that can consume it coherently; CCCL itself falls back to non-cacheable DAX + DMA. **None of these beats the frozen lookaside plan for a 4-page Letters contribution.**

### RESEARCH QUESTION 2 — Feasibility of the frozen implementation

**GPU BBDev PMD backed by OpenCL/SYCL — feasible, moderate-high effort.** The BBDev PMD contract is well-defined: implement device probe, queue setup, and `enqueue_ldpc_dec_ops`/`dequeue_ldpc_dec_ops` against `rte_bbdev_op_ldpc_dec` (which carries base graph BG1/BG2, Zc lifting size, Ncb, Qm, filler bits, iteration count, and optional HARQ combined input/output buffers). CB-mode is the baseline; TB-mode is documented as "currently not supported" even in DPDK's own text, so the PMD can legitimately start CB-mode-only. The mbuf/mempool model fits a userspace GPU PMD: the PMD copies (or DMAs) the LLR input mbuf to the GPU, launches the OpenCL kernel, and writes the hard-output mbuf.

- **`gpudev` status (a real gotcha the doc must address).** DPDK's `lib/gpudev` still exists (present through 25.07/26.03 docs) but its non-CUDA value is minimal: it is explicitly *out of scope* for launching workloads ("not possible to launch workload on the device or create GPU specific objects … CUDA Driver context or CUDA Streams"), and its only real driver backend is NVIDIA's CUDA driver library (needs CUDA + GDRCopy). So `gpudev` **does not help** a portable OpenCL PMD — the PMD must manage GPU memory/queues itself via OpenCL/SYCL. State this plainly: the PMD is self-contained, not built on gpudev.
- **Upstreaming politics.** DPDK accepted NVIDIA's CUDA `gpudev`, but the community is wary of vendor-GPU code. A BSD-3 OpenCL PMD that is genuinely vendor-portable has a better upstream story, but expect a long review; targeting a specific LTS and shipping out-of-tree first (as AccelerComm did with its T2 patch against DPDK 20.11) is the pragmatic path.

**OAI integration reality.** The `nrLDPC_coding` plugin is the correct, mature seam. The documented T2 flow uses **DPDK 20.11.9 + an AccelerComm patch** (`ACCL_BBDEV_DPDK20.11.3_ldpc_3.1.918.patch`) and `shlibversion "_t2"`; OAI MR !3344 generalized this to any BBDev accelerator (ACC100/200) with an `llr_scaling` step. srsRAN's story is weaker — it has hardware-accelerator/BBDev hooks but the mature, documented BBDev/AAL path is OAI's. **Hidden killer — HARQ soft-buffer management.** The ACC100 keeps HARQ combined buffers *on-card* (`RTE_BBDEV_LDPC_INTERNAL_HARQ_MEMORY_IN_ENABLE`); a lookaside GPU PMD must either (a) stream HARQ LLR buffers across PCIe every retransmission (bandwidth + latency cost) or (b) keep a HARQ soft-buffer pool resident in VRAM and manage its lifecycle keyed by HARQ process ID. Getting this wrong breaks IR-HARQ correctness. **This is the single most important implementation risk** — the safe first deliverable advertises capabilities *without* internal HARQ, benchmarks single-shot decode, then adds HARQ combining as a second milestone.

**Slot-budget arithmetic.** The anchor (CPU 11,703 µs/slot = 23.4× over 500 µs) motivates offload. For a full 100 MHz / 273-PRB / MU-MIMO slot, LDPC decode spans dozens of code blocks; the GPU must **batch all CBs of a slot into one kernel launch** to amortize launch overhead. This is where the compute choice bites. Per SYCL-Bench 2020 (Lettich et al., ACM IWOCL, DOI 10.1145/3648115.3648120): "the DPC++ AMD backend suffers from high scheduling overhead … with a 7x slowdown compared to the same benchmark running with AdaptiveCpp and 14x slowdown compared to the one running on the Tesla V100S." Practical implication on AMD: use **AdaptiveCpp, not DPC++**, batch aggressively, and use persistent/in-order queues. PoCL is fine for functional/bit-exactness testing but not for latency numbers. A realistic budget must include H2D DMA of LLRs, single batched kernel launch, decode, and D2H of hard bits — the round trip is precisely why inline exists, but for a lookaside Letters result the batched single-launch budget is plausibly within slot for moderate configs and should be **measured, not asserted**.

**CXL claims — the weakest technical section.** Can a discrete PCIe GPU access CXL Type-3 memory today? Per CCCL/CXL-CCL (arXiv:2602.22457), **yes, but only as a pinned host buffer via streaming DMA, not as coherent GPU load/store.** Their setup: each of 3 nodes has an Intel Xeon 6960P (72 cores) + 256 GB DRAM + one discrete NVIDIA H100 (80 GB) on PCIe Gen5×16, a TITAN-II (Xconn) CXL 2.0 switch, and a 768 GB pool of six Micron CZ120 128 GB Type-3 cards; they "disable the DDIO … set the memory pool address space as non-cacheable," `mmap` `/dev/dax0.0`, then use **`cudaHostRegister` + `cudaMemcpyAsync`** (explicitly "GPU DMA"), reaching ~20 GB/s at 1 MB transfers and 658 ns MLC latency versus 214 ns local DRAM (3.1×); software was Linux 6.2.6, CUDA 12.8. The CPU can do direct load/store to the DAX region; **the GPU cannot — it uses a DMA copy stage.** This exactly validates the doc's "no zero-copy; streaming DMA ~20 GB/s / ~660 ns" framing (the doc's "660 ns" is a rounding of 658 ns). **BUT**: the doc plans OpenCL/SYCL on AMD, and there is **no demonstrated OpenCL or `hipHostRegister` equivalent of pinning a DAX-mapped CXL region for AMD-GPU DMA.** OpenCL `clImportMemoryARM`/SVM/`CL_MEM_USE_HOST_PTR` paths for registering arbitrary DAX host memory for AMD-GPU DMA are unproven. This is a genuine incompatibility landmine.

**QEMU CXL + PoCL validation — reviewers will push back.** QEMU CXL is functional-only: per CXL-DMSim (arXiv:2411.02282), it "does not model the physical characteristics and internal micro-architecture of CXL devices … unsuitable for architectural exploration and accurate performance evaluation." Volatile Type-3 support historically required out-of-tree branches (Jonathan Cameron's jic23 tree), and QEMU does not emulate a coherency protocol. So QEMU CXL can demonstrate *functional* NUMA-node placement and software correctness, but **any latency/bandwidth number from QEMU CXL is not defensible**, and a Letters reviewer from the systems/networking community would reject performance claims built on it. PoCL is likewise for functional bit-exactness, not latency. This is acceptable *only if framed as functional validation*, with the performance story deferred to hardware.

**IISc HACC hardware (confirmed, verbatim from amd-haccs.io/iisc.html).** IISc's HACC (Profs. R. Govindarajan and Chiranjib Bhattacharya, CSA) comprises "Three nodes of 2Px96C Genoa with 764GB DDR5, each having four AMD Instinct™ MI210 Accelerators … There is one 2Px64C Milan system with 640GB RAM DDR4, having two Alveo V70 AI Accelerator cards." **Critical for this proposal: there is no CXL memory and no NVIDIA/Mellanox NIC.** Consequences: (a) CXL hardware validation **cannot** be done at IISc HACC — it needs a different facility or stays QEMU-functional-only; (b) the GPU is MI210 (ROCm/CDNA2, gfx90a), well-supported by ROCm and AdaptiveCpp but pushing you onto ROCm OpenCL or rusticl rather than a portable ideal; (c) the "open dmabuf NIC→GPU" demo needs an mlx5 NIC that HACC does not list. This materially reshapes what can be demonstrated.

**Publication fit.** A 4-page IEEE Networking/Communications Letters can support **one crisp result**: "first GPU BBDev PMD; bit-exact OpenCL LDPC decode via the open AAL seam; benchmarked vs CPU BBDev software and ACC100." That is a legitimate Letters contribution. The full "open zero-copy inline + CXL pooling + GPU-initiated networking" vision is an **NSDI/ATC/EuroSys systems paper** or an O-RAN/MobiCom workshop paper — too many moving parts and hardware dependencies for Letters. Recommendation: publish the PMD as the Letters paper; keep CXL/inline as the systems follow-on.

### RESEARCH QUESTION 3 — Incompatibility landmines (stack-seam matrix)

**Recommended known-good configuration (for IISc MI210 hardware):**

| Seam | Recommended known-good | Landmine to avoid |
|---|---|---|
| SYCL runtime × GPU | **AdaptiveCpp** (generic SSCP or `hip:gfx90a`) on MI210 | DPC++ HIP backend: ~7× kernel-launch overhead on AMD (SYCL-Bench 2020); avoid for latency-critical batching |
| OpenCL impl on AMD | **ROCm OpenCL** on MI210 (CDNA2/gfx90a supported) | rusticl works (Mesa/RadeonSI, passes OCL 3.0 CTS) but is not tuned for Instinct; AMD dropped consumer PAL OpenCL in 2020 |
| dmabuf export (GPU side) | ROCm `hsa_amd_portable_export_dmabuf` + large-BAR + IOMMU passthrough | Requires same PCIe root complex; `nvidia-peermem` broken on kernel ≥6.8 (N/A for AMD, relevant only for any NVIDIA control node) |
| NIC dmabuf import | **mlx5 (ConnectX-6 Dx+)** — only mature importer | irdma/E810 dmabuf is a narrow later patch; Broadcom/others unproven; **HACC lacks mlx5** |
| OpenCL external memory | `cl_khr_external_memory` / `cl_arm_import_memory` (dmabuf) | Uneven vendor support; **prototype dmabuf-import-into-CL-kernel before freeze** |
| DPDK × OAI | DPDK LTS matching OAI's flow (20.11.x baseline; validate against a current LTS 23.11/24.11) + `nrLDPC_coding` `_t2`-style shlib | BBDev API is stable but ABI version bumps across LTS; a new PMD must target the LTS OAI builds against |
| CXL Type-3 system-ram | kernel 6.x + `cxl create-region` + `daxctl` → NUMA node; `numactl` onnode | QEMU CXL = functional only, no valid perf; volatile Type-3 needs recent kernel/QEMU; **no AMD-GPU DMA-from-DAX proven** |
| HARQ | Start with **no internal HARQ**, single-shot decode | On-card HARQ semantics (ACC100) don't map to a lookaside GPU; IR-HARQ correctness risk |
| Licensing | cuPHY is **Apache-2.0** (github.com/NVIDIA/aerial-cuda-accelerated-ran); DPDK is **BSD-3**; OAI is **OAI Public License v1.1** | Apache-2.0 → BSD-3 upstreaming is awkward (patent clause/attribution); keep cuPHY-derived code out of the DPDK PMD |
| O-RAN AAL | Contribute an "AAL FEC GPU profile" via Nokia WG6 membership (AALI-C/AALI-P) | WG6 AAL is spec-level; DPDK BBDev is the de-facto FEC realization but a "GPU profile" is not yet standardized |

**Licensing detail.** cuPHY being Apache-2.0 means you can *read and learn from* it, but porting Apache-2.0 kernel code into a BSD-3 DPDK PMD for upstreaming is legally awkward (Apache-2.0 carries a patent grant and attribution requirements and is one-way-compatible into GPLv3, not cleanly into permissive BSD-3). Since the user already has their **own** bit-exact OpenCL LDPC kernel (BG1/BG2, Z=384/256, 0-mismatch), the cleanest path is to keep the PMD 100% original/BSD-3 and never link cuPHY — use cuPHY only as a reference oracle for test vectors. This side-steps the conflict entirely. (Note: the cuPHY repo README states "Aerial is not accepting contributions at this time," so upstreaming into it is not an option regardless.)

## Recommendations

**Stage 1 (Letters paper, near-term): Ship the GPU BBDev PMD.**
- Build a self-contained BSD-3 OpenCL-backed BBDev PMD (do NOT build on `gpudev`; do NOT link cuPHY). CB-mode LDPC decode, BG1/BG2, no internal HARQ initially.
- Load it via OAI `nrLDPC_coding` `_t2`-style shlib. Benchmark bit-exactness (already 0-mismatch) and per-slot latency vs. CPU BBDev software decoder and Intel ACC100, on **MI210 via AdaptiveCpp** at IISc HACC.
- Frame novelty as "first GPU BBDev PMD + portable open AAL seam," citing that all extant BBDev PMDs are FPGA/ASIC. Defensible and publishable.
- **Benchmark threshold that would change the plan:** if batched single-launch decode of a full 273-PRB slot on MI210 cannot get within ~2× of the 500 µs budget, the lookaside-per-slot latency story is too weak for a strong Letters claim → pivot to a throughput/energy framing (as "Six Times to Spare" does) rather than latency-headroom.

**Stage 2 (validate the datapath, systems follow-on): dmabuf NIC→GPU.**
- Only attempt if an **mlx5 NIC** can be placed on the same root complex as an MI210. Prototype `ibv_reg_dmabuf_mr` → OpenCL `cl_khr_external_memory` import → kernel reads VRAM.
- **Threshold / freeze-breaker:** if the NIC-dmabuf→CL-kernel chain cannot be made to work on ROCm OpenCL within a bounded ≤2-week spike, treat SYCL/OpenCL dmabuf interop as a confirmed blocker and escalate to the compute-choice fallback below.

**Stage 3 (defer, as the doc already says): GPU-initiated networking and inline L1.** Keep as Track 2. Track UCCL-EP and NCCL-GIN Proxy as the open baselines, but note they are CPU-proxy and AI-collective-oriented; there is no open eCPRI GPU-initiated result to build on.

**§8 decisions — unfreeze recommendations (direct, non-sycophantic):**
- **UNFREEZE the CXL Type-3 validation claim.** As written, "CXL Type-3 as system-ram NUMA shared between CPU and GPU" implies GPU access that CCCL shows is streaming-DMA-only on NVIDIA and **unproven on AMD**, and IISc HACC has **no CXL hardware**. Demote CXL to a clearly-labelled *functional/QEMU-only, forward-looking* section, or cut it from the Letters paper entirely. Do not claim CXL performance numbers.
- **KEEP FROZEN but gate the compute choice (SYCL/OpenCL).** It is the right open choice, but add a pre-freeze gate: prove dmabuf import + acceptable batched-launch latency on MI210/AdaptiveCpp *before* full commit. If interop fails, the fallback is HIP/ROCm (still far more open than CUDA and native to MI210) for the datapath, while keeping OpenCL for the compute kernel itself.
- **KEEP FROZEN:** lookaside-first, Track-2 deferral, DMA-BUF+RoCE ingress, AAL/BBDev seam, and the "portable + open standards" differentiation (not "first open GPU RAN," since cuPHY is now Apache-2.0). All validated as correct.
- **CORRECT the "open datapath is vendor-neutral" implication.** State explicitly that dmabuf NIC→GPU currently requires mlx5 NICs — the datapath is open at the *verb* level (`ibv_reg_dmabuf_mr`) but NIC-locked in practice.

## Caveats
- **All cited papers/repos verified to exist and are characterized correctly.** *Six Times to Spare* (arXiv:2602.04652, Barker et al.): DGX Spark / integrated Blackwell GB10; "we observe an average GPU/CPU throughput speedup of approximately 6×, with per-codeword CPU latency reaching ≈0.71 ms at 20 iterations (exceeding the 0.5 ms slot), while the GB10 GPU remains within 6–24% of the slot for the same workloads"; the authors explicitly note "the reliance on high-level Python and TensorFlow layers, rather than hand-tuned CUDA kernels, which means the reported benefits represent a conservative lower bound on achievable accelerator performance" (Sionna 1.2.1 PHY/SYS, TensorFlow 2.17, k=512→n=1024, R=1/2). *CCCL/CXL-CCL* (arXiv:2602.22457): discrete H100 + TITAN-II/Xconn CXL 2.0 switch + six Micron CZ120 128 GB Type-3 cards (768 GB pool), ~20 GB/s at 1 MB, 658 ns vs 214 ns DRAM (3.1×), `cudaHostRegister`+`cudaMemcpyAsync` streaming DMA, DDIO disabled/non-cacheable, Linux 6.2.6 + CUDA 12.8. *DecodeX* (arXiv:2511.02952): benchmarks FlexRAN/Aerial/Sionna-RK/ACC100; confirms OAI's CUDA LDPC decoder is lookaside and Aerial is inline. *UCCL* (arXiv:2504.17307) and *UCCL-EP* (arXiv:2512.19849, OSDI'26): CPU-proxy, Apache-2.0. *GIN* (arXiv:2511.15076): dual GDAKI/Proxy backend. *Open cuPHY* (github.com/NVIDIA/aerial-cuda-accelerated-ran): Apache-2.0, "not accepting contributions."
- **The "660 ns" figure is 658 ns in CCCL** — a rounding; fine to cite as "~660 ns."
- **The "Six Times to Spare" GPU is integrated (GB10), not discrete PCIe.** Its 6–24%-of-slot envelope does not include a discrete-GPU PCIe round trip, so it is an optimistic reference for a lookaside discrete-GPU design; the doc should note this.
- **eCPRI / 500 µs feasibility of open GPU-initiated networking is unproven** — no published open result exists; all evidence is from AI-collective workloads with looser latency tolerance.
- **IISc HACC lacks CXL and mlx5** (verified hardware list: MI210 GPUs, Alveo V70; Genoa/Milan CPUs), which constrains Stages 2–3 to functional-only or a different facility.
- Source quality: DPDK, rdma-core, ROCm, Khronos, O-RAN, and OAI primary docs plus arXiv primaries were prioritized; NVIDIA vendor blogs were used only for architectural framing (inline vs lookaside), never for performance claims.
