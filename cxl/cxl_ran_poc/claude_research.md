# Feasibility Study: A Paper-Quality PoC Combining CXL Emulation, Accelerator Simulation, 5G NR L1 Workloads, and eBPF Interception on Commodity Linux

## TL;DR
- **The PoC is feasible and publishable as a functional/architectural demonstration, but NOT as a timing-accurate or hardware-coherency result.** Build it as: QEMU (≥9.x) CXL Type-3 volatile memory exposed as a NUMA node + file-backed shared memory for the "accelerator" data path + a CPU-based "GPU daemon" (OpenCL/SYCL via PoCL or oneAPI CPU runtime) + srsRAN/OAI standalone LDPC+FFT kernels + eBPF uprobes for interception. Use NUMA latency emulation (Pond-style) or CXLMemSim/Mess for any latency claims, because QEMU does not model CXL timing or coherency.
- **The exact four-way combination (QEMU-CXL + simulated accelerator + OAI/srsRAN L1 + eBPF-uprobe transparent offload) appears unpublished.** Closest prior art: AtlasRAN (RAN + accelerator offload + coherent memory, but on DGX hardware), eGPU (eBPF + GPU + CXL.mem emulation), and UDON (NUMA-emulated CXL Type-2 compute offload). The novel, unclaimed contribution is the eBPF-uprobe transparent LDPC/FFT interception layer routing compute through emulated CXL shared memory.
- **Hardware: a workstation, not a laptop, is the realistic target.** Budget 32–64 GB RAM and 8+ physical cores. A laptop can run a reduced functional demo (small CXL window, RFsim phy-test, single-thread LDPC), but the full stack with srsRAN PHY benchmarks, a GPU daemon, and a CXL-enabled custom kernel needs workstation headroom.

## Key Findings

### CXL emulation
- **QEMU is the only functional CXL device emulator**, and base CXL 2.0 Type-3 support (memory expanders, root ports, host bridges on x86) first merged in **QEMU 7.1 (Aug 2022)**, authored by Jonathan Cameron (Huawei), originally started by Ben Widawsky (Intel). Volatile and multi-region Type-3 support (the `volatile-memdev`/`persistent-memdev` options) merged around **QEMU 8.1 (Aug 2023)** via Gregory Price (MemVerge). Dynamic Capacity Device (DCD, CXL 3.0) emulation followed in 2024 patch series.
- **QEMU CXL is functional-only — it does NOT model latency/timing and does NOT emulate the CXL coherency protocol.** The QEMU docs state cache operations are "mostly irrelevant to QEMU emulation as QEMU is not emulating a coherency protocol," and the CXL-on-QEMU community confirms QEMU "is not suitable for performance related simulation and evaluation." This is the single most important constraint for the PoC.
- **CXL Type-2 (accelerator / CXL.cache) is NOT in mainline QEMU — only RFC/experimental.** Key efforts: Ira Weiny's (Intel) Type-2 RFC (May 2023) mocking Back-Invalidate/Unordered-IO, and Zhi Wang's (NVIDIA) `cxl-accel` device patches (Dec 2024) intended as a base for vfio-cxl Type-2 passthrough. **You cannot faithfully emulate a coherent CXL accelerator in QEMU today.**
- QEMU CXL exercises the real Linux kernel CXL subsystem (`drivers/cxl/`); CONFIG_CXL_BUS, CONFIG_CXL_MEM etc. must be enabled, and kernels from roughly 6.x onward work (community reports of success on 6.6+; specific custom branches recommended for volatile/DCD). The emulated Type-3 device surfaces as `/dev/cxl/memN`, then via `cxl create-region` and `daxctl` becomes a system-RAM NUMA node.
- **Other CXL simulators:** CXLMemSim (UCSC; SlugLab; Yang, Safayenikoo, Ma, Khan, Quinn; arXiv:2303.06153, YArch'23) — a pure-software CXL.mem latency injector using epoch-based tracing and a timing model that "requires no modifications to the target program or special hardware … runs orders of magnitude faster than cycle-accurate simulators (e.g., Gem5)," making it the best fit for the "standard dev machine" constraint; CXL-DMSim (gem5-based full-system, "rigorously verified against a real hardware testbed with both FPGA-based and ASIC-based CXL memory prototypes … at an average simulation error of 4.1%," but cycle-level and slow, x86-only); emucxl (IIT Bombay, NUMA-based virtual appliance + userspace library); Mess (BSC, MICRO 2024, bandwidth-latency-curve model, 0.4–6% error, most accurate timing model); gem5-CXL (immature).

### emucxl specifically (IIT Bombay)
- emucxl (Raja Gond and Purushottam Kulkarni, IIT Bombay; arXiv:2404.08311, Apr 2024) is delivered as a **QEMU VM configured with two virtual NUMA nodes**: one mapped to physical CPU+memory ("host"), the second mapped to memory on a *different physical socket* with **no CPUs assigned** (a "CPU-less" node), mirroring the Pond approach. Memory access to the second node incurs the cross-socket latency penalty, approximating CXL disaggregated-memory latency. It provides a userspace library (`libemucxl` with init/exit/alloc API) and was demonstrated on a queue and a key-value store. **It does not emulate CXL protocol or accurate device latency — it approximates NUMA-like latency only.**

### GPU / accelerator simulation
- **Full cycle-accurate GPU simulators exist but are heavyweight and slow:** GPGPU-Sim (CUDA/OpenCL, ~0.8 KIPS), MGPUSim (multi-GPU, ~27 KIPS, 16–33× faster than GPGPU-Sim/Multi2Sim), gem5-gpu and the AMD gem5 APU model (runs ROCm full-system). These are not practical to run *inside* a QEMU VM alongside a RAN stack; they run as standalone simulators.
- **For this PoC, a CPU-based "GPU daemon" is the recommended simpler approach** — it proves the offload architecture (interception → CXL shared-memory handoff → accelerator compute → result return) without full GPU simulation. Implement the accelerator kernel in OpenCL or SYCL and run it on a CPU OpenCL/SYCL runtime: **PoCL** (Portable Computing Language, v7.x) exposes the CPU as an OpenCL device, and **Intel oneAPI DPC++** exposes the CPU via `ONEAPI_DEVICE_SELECTOR=opencl:cpu` (TBB-backed). This keeps everything on one commodity machine and is honest about being a functional, not performance, model of a GPU.
- **AMD's virtio-gpu DRM native context for ROCm/compute reached upstream in 2025:** the AMDGPU DRM native-context QEMU patch series by Dmitry Osipenko (Collabora) progressed through v5 (Jan 2025) and was merged by **v12/v13 (May–June 2025)**; AMDGPU DRM native context is described as "completely upstreamed" in the v12 cover letter, with the Mesa side merged for Mesa 25.0. However, this requires a **real host GPU** (it passes the guest through to native host drivers), so it does NOT satisfy the "no GPU required" constraint. virtio-gpu Venus/native-context is graphics/compute passthrough, not GPU simulation.

### 5G NR L1 workloads
- **srsRAN Project and OpenAirInterface both implement 5G NR L1 with optimized LDPC and FFT.** srsRAN advertises "highly optimized LDPC and Polar encoder/decoder for ARM Neon and x86 AVX2/AVX512." Both run as pure-software vRAN on commodity x86 with no SDR via virtual-radio modes (OAI `--rfsim`, srsRAN ZMQ RF driver).
- **OAI RFsim runs inside VMs as established practice** — OAI's own CI uses `ci-scripts/runTestOnVM.sh` to run softmodems with `--rfsim` in Ubuntu VMs. RFsim is explicitly "not designed to run close to real-time," which is fine for a functional PoC (use `--phy-test`/`noS1` modes). In OAI, the LDPC decoder is a hot-swappable shared library, and `max_ldpc_iterations` is tunable (default 8) — ideal for an interception target.
- **Standalone LDPC/FFT for BG1/BG2 without the full stack:** srsRAN ships standalone `ldpc_encoder_benchmark`, `ldpc_decoder_benchmark`, and `pusch_processor_benchmark` binaries that exercise BG1/BG2 LDPC directly. These are the cleanest interception/offload targets — you can demonstrate the PoC against these microbenchmarks before integrating the full softmodem.
- **Compute profile:** srsRAN's `pusch_processor_benchmark -m latency` (full RX chain incl. LDPC decode) reports per-transport-block latency from ~16.6 µs (RB=25 QPSK) to ~427–450 µs (RB=270 16QAM) in microseconds. An external AVX-512 LDPC reference reports 53–131 Mbps/core at 10 iterations; another Xeon AVX implementation hit 31 µs latency at 270 Mbps. The arXiv "Six Times to Spare" paper (2602.04652, Feb 2026) found CPU per-codeword LDPC latency reaching ~0.71 ms at 20 iterations — **exceeding the 0.5 ms slot** — while a Blackwell GB10 GPU stayed within 6–24% of the slot, an ~6× average speedup; CPU decoding consumed ~10 Grace cores vs. the GPU adding only ~10–15 W. This is the quantitative motivation for offload.
- **The 5G NR timing budget:** FR1 numerology µ=1 (30 kHz SCS) gives 2 slots per subframe → **slot/TTI = 0.5 ms**, within which the entire L1 RX chain (FFT, channel estimation, demapping, LDPC decode, HARQ) plus MAC scheduling must complete.

### eBPF feasibility
- **eBPF uprobes work inside QEMU/KVM VMs** (the Cloudflare benchmark for kprobes/tracepoints was itself run under QEMU on an M1). uprobes attach via INT3 breakpoint injection and require two context switches per hit.
- **Overhead: ~1670 ns per uprobe-based eBPF intercept.** Verbatim from the cloudflare/ebpf_exporter benchmark (Linux v6.7-rc3): "BenchmarkUprobeWithNoMap/cgo … 1695.00 ns/op; BenchmarkUprobeWithSimpleMap/cgo … 1717.00 ns/op; BenchmarkUprobeWithComplexMap/cgo … 1833.00 ns/op … Here overhead is a lot bigger, ~1670ns per call." A single uprobe round-trip costs roughly 1.7 µs.
- **Latency implication for 5G:** the 0.5 ms TTI is ~300× the single-uprobe cost, so interception at the *transport-block* or *slot* granularity (a handful of uprobes per slot) is comfortably within budget. Interception at fine granularity (per codeblock, thousands per slot) would blow the budget — **the architecture must intercept at coarse granularity.** This is a key design finding.
- **Kernel versions:** `BPF_MAP_TYPE_RINGBUF` was introduced in **Linux 5.8** (Andrii Nakryiko); `BPF_MAP_TYPE_USER_RINGBUF` (user→kernel direction, useful for submitting offload requests) in **Linux 6.1** (commit 583c1f4, Dave Marchevsky). The ring buffer is a multi-producer single-consumer queue with epoll-based wakeup; it can easily handle sub-millisecond signaling at slot granularity.
- No specific published issues with eBPF uprobes accessing CXL memory were found; since emulated CXL surfaces as ordinary NUMA system RAM, eBPF access should behave like normal memory.

### Full-stack feasibility & closest existing work
- **No published work combines all four elements.** The three nearest neighbors: **AtlasRAN** (arXiv:2603.14661, Feb 2026 — evaluates coherent memory + accelerator offload for RAN, OAI RFSim vs Sionna Research Kit offloading LDPC to CUDA, but on DGX Spark hardware, not QEMU); **eGPU** (Yiwei Yang et al., bpftime-based — eBPF + GPU + CXL.mem emulation with a dynamic delay model, the closest CXL+eBPF+accelerator triad); **UDON** (Hermes et al., Arm, arXiv:2404.02868 — uses Arm AArch64 dual-socket NUMA to emulate CXL Type-2, offloading ML/vector-DB kernels to near-memory cores: "Offloading Hierarchical Navigable Small World (HNSW) kernels in vector databases can provide upto 6.87× performance improvement with under 10% offload overhead," and ML inference can "place up to 90% data in remote memory with just 20% performance trade-off"). Also relevant: "Offloading to CXL-based Computational Memory" (arXiv:2512.04449) and DecodeX (arXiv:2511.02952, LDPC across CPU/GPU/ASIC).
- **QEMU alone is sufficient to host the functional stack** (CXL Type-3 + OAI RFSim + eBPF + CPU GPU-daemon simultaneously), but real-time RAN L1 deadlines are NOT achievable inside emulated CPUs — run RFsim in non-real-time/phy-test mode for functional validation only.

### Paper validation standard
- **NUMA-based ("computeless remote NUMA node") emulation is the de-facto accepted CXL emulation method at top venues.** Pond (Li et al., ASPLOS '23, arXiv:2203.00241, Microsoft Azure/VT/Intel) emulates CXL by disabling all cores on a remote NUMA socket: "On Intel, we measure 78ns NUMA-local latency and 80GB/s bandwidth and 142ns remote latency and 30GB/s bandwidth (3/4 of a CXL ×8 link)," with small 8–16-socket pools adding "only 75–90ns relative to NUMA-local DRAM" (up to 255ns remote latency on lab servers). TPP (ASPLOS '23, Meta) used CXL-emulated tiered memory; emucxl, HybridTier, and many others build on this. So an emulation-only methodology has strong precedent — **but every such paper explicitly notes the fidelity gap (no real coherency/timing), and reviewers expect that caveat plus, ideally, a latency model (CXLMemSim/Mess) or a sensitivity analysis.**
- QEMU CXL emulation is the accepted platform for *functional* CXL kernel/driver work (the Linux CXL subsystem itself was developed against QEMU), not for *performance* claims. For a systems paper, combine QEMU (functional correctness, driver path, kernel integration) with NUMA or CXLMemSim/Mess (latency sensitivity) to be defensible.

## Details

### Recommended emulation stack
1. **Host:** Linux workstation, kernel 6.6+ (6.1 minimum for USER_RINGBUF), 32–64 GB RAM, 8+ physical cores, ideally dual-socket or NUMA-capable for Pond-style latency emulation.
2. **CXL layer:** QEMU 9.x/10.x with `-machine q35,cxl=on`, a `pxb-cxl` host bridge, `cxl-rp` root port, and a `cxl-type3` volatile device backed by `memory-backend-file,share=on`. Bring it online as a system-RAM NUMA node via `cxl create-region` + `daxctl reconfigure-device -m system-ram`. The `share=on` file backing gives software-controlled cache coherency between the RAN process and the accelerator daemon — this is your shared-memory data path.
3. **Accelerator:** a CPU "GPU daemon" running an OpenCL/SYCL LDPC+FFT kernel via PoCL or oneAPI CPU runtime, reading/writing the CXL shared-memory region. Optionally swap in GPGPU-Sim/MGPUSim offline to produce projected GPU timing numbers for the paper.
4. **RAN workload:** srsRAN standalone `pusch_processor_benchmark`/`ldpc_decoder_benchmark` (cleanest), or OAI `nr-softmodem --rfsim --phy-test` with the LDPC shared library as the interception target.
5. **Interception:** eBPF uprobes on the LDPC decode / FFT entry points, with a `BPF_MAP_TYPE_RINGBUF` (kernel→user) for telemetry and `BPF_MAP_TYPE_USER_RINGBUF` (user→kernel) for control, intercepting at transport-block/slot granularity.
6. **Latency fidelity:** for timing claims, layer CXLMemSim or Mess, or use Pond-style remote-NUMA latency, and present results as a sensitivity analysis rather than absolute hardware numbers.

### What is production-ready vs experimental vs broken
- **Production-ready / mainline:** QEMU CXL Type-3 (volatile + persistent) and the Linux `drivers/cxl/` subsystem; srsRAN/OAI software PHY; eBPF uprobes + ring buffers; PoCL/oneAPI CPU OpenCL.
- **Experimental:** CXLMemSim, CXL-DMSim, emucxl, Mess (research-grade); AMD virtio-gpu DRM native context (upstreamed but needs a real GPU); DCD emulation.
- **Broken / absent for this purpose:** QEMU CXL Type-2 coherent-accelerator emulation (RFC only); any expectation of accurate CXL latency or hardware coherency from QEMU; real-time RAN L1 inside emulated CPUs.

## Recommendations
1. **Stage 1 — Functional spine (lowest risk):** Stand up QEMU CXL Type-3 volatile memory as a NUMA node and verify the kernel CXL path (`cxl list`, daxctl system-ram). Then demonstrate eBPF-uprobe interception of srsRAN's standalone `ldpc_decoder_benchmark`, routing the codeblock through the CXL shared-memory region to a CPU OpenCL daemon and back. This proves the architecture end-to-end with no GPU and no special hardware. **Benchmark/threshold to proceed:** correct LDPC output bit-for-bit through the offload path, and per-intercept overhead measured (~1.7 µs target).
2. **Stage 2 — RAN integration:** Replace the microbenchmark with OAI `nr-softmodem --rfsim --phy-test`, intercepting the LDPC shared library at transport-block granularity. Confirm functional decode and measure offload overhead per slot. **Threshold:** if per-slot interception overhead approaches the 0.5 ms TTI, coarsen granularity; if it stays well below (it should, at ~µs per intercept), proceed.
3. **Stage 3 — Latency/fidelity claims:** Add CXLMemSim or Mess (or Pond-style NUMA latency) to model realistic CXL access latency, and run a sensitivity analysis (vary injected latency across the realistic ~140–255 ns CXL range, anchored on Pond's measured 142 ns remote / 255 ns lab-server figures and reported real CXL.mem load-to-use of ~150–175 ns). Optionally run the kernel under GPGPU-Sim/MGPUSim offline to produce projected real-GPU timing. **This is what elevates the work from a functional demo to a defensible systems paper.**
4. **Framing for reviewers:** Position the contribution as the *transparent eBPF-uprobe interception + CXL-shared-memory offload architecture* (the unclaimed novelty), validated functionally in QEMU and characterized for latency via NUMA/CXLMemSim. Explicitly state the fidelity caveats up front — top-venue CXL papers (Pond, TPP) do exactly this.
5. **Hardware decision:** Use a workstation. Reserve a laptop only for a stripped functional demo.

## Caveats
- **QEMU does not model CXL timing or coherency** — all absolute latency numbers must come from a latency model (CXLMemSim/Mess) or NUMA emulation, not QEMU itself. NUMA emulation is acknowledged to *under-represent* true CXL latency: CXL-DMSim measured CXL-FPGA at ~2.88× and CXL-ASIC at ~2.18× local-DDR latency, whereas remote-NUMA emulation is typically only ~1.5× DDR-local; real CXL.mem load-to-use latency is ~150–175 ns.
- **CXL Type-2 / CXL.cache coherent accelerator behavior cannot be faithfully emulated** in mainline QEMU; the PoC must use file-backed shared memory with software coherency, and should frame the "accelerator on CXL" as a Type-2 *architecture* validated via Type-3 + shared memory.
- **Real-time RAN L1 deadlines are unattainable in emulation** — the PoC validates functional correctness and architectural overhead, not real-time slot compliance.
- **Several key references are 2026 preprints** (AtlasRAN 2603.14661, Six Times to Spare 2602.04652) and not yet peer-reviewed; treat their numbers as indicative.
- srsRAN latency figures cited come from a GitHub Discussion (user-posted benchmark output), not an official datasheet, and the exact CPU was not stated; reproduce them on your own hardware before citing in a paper.
- The ~1670 ns uprobe figure is from a Go→C benchmark harness and includes some FFI overhead; a pure-C uprobe may be modestly faster, but the order of magnitude (~1 µs) is robust.
